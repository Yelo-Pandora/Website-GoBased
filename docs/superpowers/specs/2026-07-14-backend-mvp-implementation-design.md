Gin 迁移方案、基础设施补强项、理论课程内容交付方式、测试策略和提交规则。

实现遵循“纵向切片、逐步闭环”：每一阶段都形成可运行、可测试、可独立审阅的
结果，完成后使用中文 Git 提交说明保存一次版本。

## 4. 当前状态与基础设施审阅

### 4.1 已验证能力

2026-07-14 已实际执行并通过：

* `go test ./...`
* `go vet ./...`
* `docker compose config --quiet`
* `docker compose build`
* `docker compose --profile images build lab-app`
* `docker compose up -d --wait`

六个常驻服务均进入健康状态。数据库包含既定八张平台表、三个实验数据库存储过程、
课程种子和受限数据库账号。Go 服务使用非 root 用户；适用服务启用了只读根文件系统、
capability 删除和 `no-new-privileges`。

### 4.2 实施前缺口

* `orchestrator` 没有挂载 `lab-nginx-config`，无法写入动态实验路由。
* Nginx 配置模板声明的输出目录与实际挂载目录不一致。
* orchestrator 镜像尚未携带资源模板、场景模板和契约。
* `MYSQL_PLATFORM_DATABASE` 表现为可配置项，但初始化 SQL 固定使用 `platform`。
* 缺少面向已有数据卷的增量数据库迁移机制。
* 临时容器全局上限、CPU 基线、Redis 上限和超时配置尚未形成统一配置模型。
* 缺少日志轮转、完整验收脚本和基础设施集成测试。
* OpenAPI 只保留少量占位端点，课程端点当前返回 404。
* 三个 HTTP 边界均未使用 Gin，且 handler 主要是路由文件中的匿名闭包。
* orchestrator、lab-app 和绝大部分 platform-api 业务仍是脚手架占位。

### 4.3 MySQL 本机管理端口

永久保留 `127.0.0.1:3306:3306` 和对应宿主机访问网络，供受信任维护人员使用数据库管理工具。
它只监听本机回环地址，不作为公网接口。
发布验收必须确认该端口没有改为监听全部网卡。

## 5. 实施方案选择

采用纵向切片方案，不采用一次性分层建设，也不采用绕过认证与控制面的实验优先方案。

主要原则如下：

* 保留 `platform-api` 模块化单体、独立 `orchestrator` 和独立 `lab-app` 三进程边界。
* 先建立安全和数据一致性约束，再开放会产生基础设施副作用的实验操作。
* 每个场景先形成一条端到端最小闭环，再增加策略和故障演示。
* 不为 MVP 提前拆分微服务，不引入消息中间件，不实现 SRS 已排除的能力。
* 每个阶段先完成测试和文档，再创建独立提交。

## 6. Go 包与依赖方向

### 6.1 platform-api

按职责拆分以下包：

* `internal/httpapi`：Gin router、middleware、handler、DTO 和错误映射。
* `internal/auth`：登录、会话、CSRF 和登录限流。
* `internal/course`：课程查询、正文读取和学习进度。
* `internal/lab`：实验状态机、归属、快照和生命周期规则。
* `internal/operation`：operationId 幂等、持久队列、租约和 Worker。
* `internal/event`：有界事件环和 SSE。
* `internal/traffic`：有界真实请求生成任务。
* `internal/balancer`：容量、状态和自适应权重算法。
* `internal/repository`：MySQL 持久化适配器。
* `internal/orchestrator`：HTTP/JSON over UDS 客户端。

HTTP handler 只负责解析请求、调用应用服务和映射响应，不直接编写 SQL、操作 Docker
或实现领域状态转换。

### 6.2 orchestrator

按高权限操作边界拆分：

* `internal/transport/uds`：Gin UDS 入口和命令响应。
* `internal/command`：命令白名单、字段校验、幂等检查和分派。
* `internal/template`：版本化模板注册表。
* `internal/docker`：受限 Docker API 适配器。
* `internal/database`：固定存储过程调用。
* `internal/nginx`：片段生成、校验、原子替换、重载和回滚。
* `internal/reconcile`：带平台标签资源的核对与清理。

orchestrator 不接收任意命令、镜像名、挂载、SQL 或 Nginx 文本。

### 6.3 lab-app

按运行模块拆分：

* `internal/httpapi`：Gin 内部接口。
* `internal/product`：商品读取和更新。
* `internal/order`：容量时间窗和订单批次统计。
* `internal/cache`：进程内 L1、Redis L2、回源和保护策略。
* `internal/runtime`：实例身份、容量和有界指标快照。
* `internal/store`：实验数据库访问。

## 7. Gin HTTP 边界设计

三个进程统一使用 `gin.New()` 构造路由，保留现有 `http.Server` 超时和优雅关闭。
orchestrator 仍只监听 Unix Domain Socket，Gin 仅作为该 HTTP server 的 handler。

统一中间件包括：

* panic 恢复并输出结构化日志；
* request ID 接收或生成；
* 结构化访问日志；
* 安全响应头；
* 统一错误响应；
* 请求体大小限制；
* 对外 API 的内容类型检查。

路由文件只注册分组和 handler 方法。例如公开 API 使用 `/api/v1` 分组，实验应用使用
`/internal` 分组。handler 采用显式依赖结构体，不在 router 中堆叠匿名业务闭包。

健康检查继续提供 `/healthz` 和 `/readyz`。Gin 迁移不得改变既有健康响应语义、
Compose 健康检查路径或 UDS 健康检查方式。

## 8. 数据与迁移设计

现有 SQL 作为初始空数据卷基线继续保留。开始业务实现前增加版本化迁移机制：

* 使用独立、短生命周期迁移进程；
* 迁移在 platform-api 启动前完成；
* 应用运行账号不获得 DDL 权限；
* 已执行版本记录在数据库迁移表；
* 迁移失败时阻止依赖服务启动，不自动跳过失败版本；
* 存储过程变更也纳入迁移版本管理。

SDS 明确平台数据库名为 `platform`。基础设施阶段将其固定为受验证的部署约束：
若 `MYSQL_PLATFORM_DATABASE` 不是 `platform`，初始化或服务启动应明确失败，避免产生
“连接到空库但脚本写入另一个库”的隐蔽错误。

## 9. 理论课程内容设计

### 9.1 存储和 API

课程正文使用 UTF-8 Markdown 文件，保存在 platform-api 的课程内容包内，并通过
`go:embed` 编译进二进制。数据库只保存课程元数据和学习进度，符合 SDS 的静态内容设计。

课程详情 API 返回：

* 课程元数据；
* 当前状态；
* Markdown 正文；
* `contentFormat: "markdown"`；
* 登录用户的可选学习进度。

最简前端可以先按保留换行的纯文本显示，后续再增加 Markdown 渲染，不影响后端契约。

### 9.2 写作规则

所有正文遵守：

* 面向已理解 HTTP 和数据库基础概念的初学者；
* 先说明问题，再说明结构变化、收益、代价和适用场景；
* 使用网购平台中的商品查询和模拟订单作为统一例子；
* 不出现具体编程语言语法、框架配置或代码教程；
* 不暗示某一种方案永远正确；
* 不复制参考文章的原句、代码或配图；
* 明确区分真实请求、教学等效负载和真实资源指标。

### 9.3 单机架构

正文至少覆盖：

* 页面入口、业务处理和数据存储都集中在一台机器上的含义；
* 部署简单、成本低、定位问题直接等优点；
* 资源相互争用、单点故障、容量上限和扩展困难；
* 纵向扩容能缓解但不能消除结构性限制；
* 适合学习、原型、小流量和可接受短暂停机的场景；
* 为什么本平台只提供理论内容而不创建单机一体化实验容器。

### 9.4 应用与数据分离

正文至少覆盖：

* 将业务处理和数据存储放到不同运行单元的原因；
* 两者通过网络通信后的请求链路；
* 独立扩容、职责清晰、数据集中管理和故障隔离收益；
* 网络延迟、连接管理、数据库可用性和新瓶颈；
* 该阶段仍不是高可用集群；
* 本平台实验中一个应用实例访问独立实验数据库的观察重点。

### 9.5 应用集群与负载均衡

参考 SRC-WEB-001 的概念范围，使用原创表述覆盖：

* 为什么增加应用实例后还需要统一流量入口；
* 负载均衡对吞吐、扩展和故障隔离的作用；
* 轮询、加权轮询、IP 哈希、最少连接和最短响应时间的直观含义；
* 每种策略的适用条件与可能造成的不均衡或额外监测成本；
* 健康检查和摘除不可用实例的重要性；
* 本平台固定权重与自适应权重的区别；
* 权重不能解决集群总容量不足这一事实。

课程不扩展到 DNS 全球调度或数据分片实验，它们只可作为后续方向简要提及。

### 9.6 Redis、多级缓存与缓存故障

参考 SRC-WEB-002 中与 Redis 有关的概念，完全排除 Caffeine 章节、依赖和示例。
本平台仍采用进程内 L1、会话 Redis L2、实验 MySQL 的现有方案。

正文至少覆盖：

* 缓存为何适合读多写少、频繁读取且较少变化的数据；
* Redis 作为多个应用实例共享缓存的作用；
* 缓存键应兼顾唯一、可读、长度可控和命名空间隔离；
* 先查缓存、未命中回源、回填并设置过期时间的基本链路；
* 随机过期时间如何降低集中失效风险；
* 进程内 L1 如何减少远程访问，以及多实例下的一致性代价；
* 商品更新后删除 L2 并通知各实例删除 L1 的失效链路；
* 缓存穿透、击穿、雪崩和 Redis 重启的现象、影响及保护思路；
* 缓存不是数据事实来源，保护策略也不能替代容量规划和降级设计。

## 10. 外部行为、错误与安全

API 路径保持 SRS/SDS 已批准边界。所有错误使用稳定业务码和一致 JSON 结构，
不向前端暴露内部 SQL、Docker、文件路径或堆栈信息。

认证使用服务端随机 session token 的哈希持久化，Cookie 使用 HttpOnly 和
SameSite=Strict。状态变更同时验证 CSRF token。当前 HTTP 部署不设置 Secure，
切换 HTTPS 后必须启用。

实验操作依次校验：认证、实验归属、实例归属、状态、动作白名单、参数范围、配额和
operationId。只有通过这些检查的操作才进入持久队列。

## 11. 后端 MVP 实施顺序

### 阶段 0A：基础设施补强

修复动态 Nginx 卷和路径、模板进入 orchestrator 镜像、平台数据库名约束、迁移入口、
资源配置、日志轮转和验收脚本。永久保留 MySQL 回环地址管理端口。

### 阶段 0B：Gin 迁移

迁移 platform-api、orchestrator UDS 和 lab-app 三个 HTTP 边界，增加公共中间件、
显式 handler 和路由测试，不引入新的业务能力。

### 阶段 1：课程和理论内容

实现知识地图、课程列表、课程详情、占位课程和学习进度，交付第 9 节规定的全部正文。

### 阶段 2：认证会话

实现登录、退出、当前用户、服务端会话、CSRF 和登录限流。
账号使用初始化脚本和宿主机本地 MySQL 管理入口维护，不实现管理员 CLI。

### 阶段 3：实验控制面基础

实现实验状态机、单活动实验、归属校验、operationId 幂等、持久操作队列、租约 Worker、
配额模型和 UDS 客户端。

### 阶段 4：安全编排器

实现模板注册表、命令校验、Docker 适配器、实验数据库存储过程适配器、Nginx 配置管理、
补偿和资源核对。

### 阶段 5：应用与数据分离闭环

实现创建实验数据库、网络和首个应用实例，完成商品查询、实验快照、重置、主动结束和
失败回滚。

### 阶段 6：事件与生命周期

实现有界事件环、SSE、断线补发、倒计时、空闲与最长时限回收，以及周期性资源核对。

### 阶段 7：应用集群和固定权重

实现扩缩容、健康检查、Nginx upstream、容量时间窗、真实低速流量、模拟订单处理/丢失、
实例状态和固定权重调整。

### 阶段 8：自适应负载均衡

实现容量派生、指标平滑、持续阈值、冷却时间、目标权重计算和安全配置应用。

### 阶段 9：多级缓存与缓存故障

实现进程内 L1、Redis L2、MySQL 回源、失效广播、穿透/击穿/雪崩保护和 Redis 重启回退。

### 阶段 10：MVP 验收与发布收尾

完成单元、集成、E2E、安全、容量和恢复测试；补齐 OpenAPI、运维说明和最简前端对接；
确认 Edge Nginx 是唯一公网入口，MySQL 管理端口仍只绑定 `127.0.0.1`。

## 12. Git 提交策略

若一个阶段过大，可以继续拆成多个中文提交，但不得把多个无关阶段压成一个提交。
已提交阶段的后续修复使用新的中文提交，不通过重写历史掩盖审阅记录。

## 13. 测试与阶段验收

每次提交至少执行：

* `gofmt`；
* `go test ./...`；
* `go vet ./...`；
* `docker compose config --quiet`（涉及部署文件时）；
* 受影响镜像构建（涉及 Dockerfile 或运行依赖时）。

关键阶段额外执行：

* Gin 路由和中间件使用 `httptest`；
* repository 和迁移使用真实 MySQL 集成测试；
* UDS 使用真实 Unix socket 集成测试；
* 编排器使用受控 Docker 测试资源和平台标签；
* Nginx 变更验证失败回滚；
* 实验场景执行端到端创建、操作、重置和销毁；
* 最终验收确认只有 edge-nginx 提供公网入口，MySQL 仅绑定宿主机回环地址。

## 14. 故障处理原则

* 外部依赖失败时保守拒绝新副作用，理论课程仍可读取。
* 队列采用至少一次执行，资源命令必须幂等。
* 创建失败按已完成步骤逆序补偿。
* Nginx 新配置验证失败时保留上一份有效配置。
* 平台启动后依据 MySQL、Docker 标签和 Nginx 片段核对事实状态。
* Redis 故障只影响所属实验，按当前策略回源或降级。

## 15. 明确排除

本实施设计不增加：

* 公开注册或管理员 Web 后台；
* 管理员 CLI；
* 任意终端、Docker 参数、SQL 或 Nginx 文本入口；
* 完整商城、支付、退款和真实库存；
* 实验评分、排行、标准答案或容器快照恢复；
* Caffeine 或任何绑定具体编程语言的课程教程；
* 消息中间件、微服务拆分、Kubernetes 或云平台实现。
