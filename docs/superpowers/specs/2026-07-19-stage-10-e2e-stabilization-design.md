# 阶段十 E2E 稳定性收敛设计

## 背景

阶段十回归中的五个失败由两个根因造成。

第一，阶段九以后 Orchestrator 对所有 Lab App 注入缓存环境变量。非缓存场景没有缓存配置，
因此收到值为零的 `CACHE_L1_MAX_PRODUCT_ENTRIES` 等变量并在启动时退出。随后 Nginx 只能报告
`host not found in upstream`，使真正的应用启动错误被误判为网关配置错误。

第二，手动批次 E2E 使用真实后端延迟，却在固定时间内断言精确请求数量。自动批次为避免堆积会在
上一请求未完成时跳过定时触发，因此该断言不能稳定证明“手动发送没有创建第二个自动循环”。

## 方案比较

1. 只修正非缓存场景变量。改动最小，但未来任何 Lab App 启动失败仍会被 Nginx 错误掩盖。
2. 只为 Nginx 增加重试。可能缓解 DNS 暂态延迟，但会等待一个已经退出的容器，不能解决根因。
3. 按场景构造环境并增加容器就绪屏障，同时隔离流量调度测试中的后端延迟。

采用方案三。

## 运行时设计

Orchestrator 先构造所有场景共享的 Lab App 环境。只有场景声明 Redis 和有效缓存配置时，才追加
Redis、L1、L2、TTL 和模拟延迟变量。非缓存场景不再传递零值缓存配置，Lab App 使用自身安全默认值，
且这些值不会进入非缓存处理器。

Docker 客户端在创建或重新启动带健康检查的容器后等待 `healthy`。容器退出、变为 `unhealthy`、
上下文取消或等待超时时，创建操作直接返回 Docker 层错误，不再继续发布 Nginx upstream。
等待时间由健康检查间隔、超时和重试次数推导并设置上限。

Nginx 保留现有原子写入、校验和回滚流程，不对永久性容器错误进行盲目重试。

## 测试设计

新增 Orchestrator 测试，验证非缓存场景不注入缓存变量，缓存场景仍使用模板中的固定值。
新增 Docker 客户端测试，覆盖健康、退出和超时路径。

手动批次 E2E 拦截批次接口并立即返回固定合法结果，使请求计数只反映浏览器调度器：手动发送只增加
一个请求，自动生成保持单循环，停止后不再产生请求。其他 E2E 继续使用真实平台、Nginx 和 Lab App。

## 验收

目标四个真实资源场景连续通过，手动批次调度场景稳定通过；随后运行 Go 单元测试、`go vet`、
前端单元测试、前端构建和完整普通 E2E。两个需要重启或短生命周期配置的专用场景继续由显式环境变量启用。
