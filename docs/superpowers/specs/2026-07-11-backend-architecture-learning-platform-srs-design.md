## 1. 文档目的

本文档定义互联网后端架构学习平台首期MVP的产品范围、系统边界、
功能需求、非功能需求、数据约束和验收标准。
平台以网购请求为统一业务背景，通过真实但低负载的Docker容器、
Nginx转发、Go服务、Redis和MySQL演示后端架构演进。

## 3. 产品目标

平台面向具备HTTP、数据库和Go基础的学习者。
目标不是建设真实商城，而是让学习者观察并操作架构变化，理解请求路径、
资源容量、负载均衡、多级缓存和故障现象。

教学遵循自由探索模式。
系统不评分、不排名、不提供唯一标准答案，只解释操作后发生的系统变化。

## 4. MVP范围

### 4.1 MVP激活课程

* 单机架构：仅提供理论内容，不创建单机一体化容器。
* 应用与数据分离：一个会话应用容器连接共享MySQL。
* 应用集群与负载均衡：一至四个应用容器和内部Nginx。
* 多级缓存：应用L1、会话Redis和共享MySQL。
* 缓存故障：穿透、击穿、雪崩和Redis重启。

### 4.2 待完成占位

* 数据库读写分离。
* 分库分表与分布式数据库。
* CDN与反向代理独立课程。
* 搜索引擎与NoSQL。
* 业务拆分与分布式系统。
* 微服务架构。
* 容器化与云平台独立课程。

Docker和Nginx是MVP运行基础设施，但其独立课程仍保持待完成状态。

### 4.3 明确排除

* 公开注册和管理员Web后台。
* 完整商城、支付、退款、真实库存和运营后台。
* 用户终端、任意Docker命令、任意Nginx配置编辑。
* 手机端完整实验体验。
* 实验评分、排行榜、标准答案和容器快照恢复。
* Kubernetes、云平台和图片中其他待完成架构实验。

## 6. 总体架构

~~~mermaid
flowchart TB
    Browser["桌面浏览器与Vue前端"] --> Edge["公网入口Nginx"]
    Edge --> API["Go平台后端"]
    API --> MySQL["共享MySQL"]
    API --> Orchestrator["内部Go编排服务"]
    Orchestrator --> Proxy["受限Docker Socket代理"]
    Proxy --> Docker["宿主机Docker Engine"]
    API --> Gateway["内部实验Nginx"]
    Gateway --> Apps["会话Go应用容器"]
    Apps --> Redis["会话Redis"]
    Apps --> MySQL
    Redis --> MySQL
~~~

公网入口Nginx与内部实验Nginx必须分离。
前者提供Vue静态文件并反向代理平台API，后者承载动态实验upstream。
浏览器不能直接访问应用容器、Redis、MySQL、编排服务或Docker API。

平台采用共享基础设施与会话临时资源混合隔离。
MySQL、入口、平台后端、编排服务和实验Nginx共享。
应用容器、缓存实验Redis和实验网络按会话创建并自动销毁。

## 7. 关键运行模型

### 7.1 负载与容量

有效容量等于实例基础容量乘以性能保留比例。
相对负载等于分配到实例的教学等效负载除以有效容量。

| 相对负载 | 后端状态 |
| ---: | --- |
| 0%至30% | idle |
| 大于30%至70% | normal |
| 大于70%至100% | high |
| 大于100% | overloaded |
| 健康检查失败 | unavailable |

前端未来的颜色和动画只能消费这些后端状态，不得自行随机生成负载结果。

### 7.2 真实流量与教学等效流量

当前浏览器页面按本地定时器生成少量真实HTTP批次请求，每个小球代表一批教学等效订单。
公开批次接口同步经过平台后端和内部Nginx，实例返回实际目标实例、processed、dropped
和处理后的负载状态。前端只负责生成批次和动画，不得自行决定路由、处理结果或服务器颜色。
教学等效请求量必须与实际HTTP请求次数同时显示，避免将模拟规模描述为真实压力。

### 7.3 自适应负载均衡

固定模式保留当前Nginx权重。
自适应模式按有效容量和稳定指标计算推荐流量比例。
控制器每两秒采样，并使用平滑、持续阈值和冷却时间抑制抖动。
任何配置应用前都必须通过nginx -t，并采用原子替换和优雅重载。

### 7.4 多级缓存

查询顺序为应用进程内L1、会话Redis L2、共享MySQL。
商品更新后删除L2，并通过Redis Pub/Sub通知各实例删除L1。
缓存实验可独立切换穿透、击穿和雪崩保护策略。

## 9. 外部接口

建议的MVP外部接口边界如下。
最终路径可在实施计划中细化，但语义和权限边界不得改变。

~~~text
GET    /api/v1/courses
GET    /api/v1/courses/:slug
POST   /api/v1/auth/login
POST   /api/v1/auth/logout
GET    /api/v1/auth/me
POST   /api/v1/labs
GET    /api/v1/labs/:id
POST   /api/v1/labs/:id/actions
POST   /api/v1/labs/:id/traffic-batches
POST   /api/v1/labs/:id/reset
DELETE /api/v1/labs/:id
~~~

部署和诊断端点独立于浏览器业务接口：

~~~text
GET /healthz
GET /readyz
GET /api/v1/system/info
~~~

`/healthz`用于容器和入口存活检查，不纳入Swagger UI的人工业务验收范围。
实验创建、拓扑调整和生命周期变更请求必须携带唯一operationId。
错误响应使用稳定业务错误码，包括AUTH_REQUIRED、LAB_NOT_OWNED、
LAB_ALREADY_ACTIVE、MIN_INSTANCE_LIMIT、MAX_INSTANCE_LIMIT、
RESOURCE_CAPACITY_EXCEEDED、DOCKER_UNAVAILABLE、
NGINX_CONFIG_INVALID和LAB_BUSY。

## 10. 数据需求

建议的持久实体包括users、auth_sessions、courses、course_progress、
lab_sessions、lab_instances、lab_operations和lab_resources。
前端生成的高频批次不单独持久化，实验应用只按时间窗口聚合订单结果。
实验结束后删除会话临时商品数据。

Docker容器、网络和Redis是运行时事实来源。
MySQL保存其标识与预期状态，用于平台重启后的资源核对。

## 13. 验证策略

验证应覆盖容量算法、权重算法、缓存策略、授权、幂等、状态机和超时的
单元级检查。
组件级验证应覆盖MySQL、Redis、内部Nginx、Docker编排、配置回滚、
资源清理和平台重启核对。
端到端验证应覆盖匿名浏览、登录、扩缩容、性能衰退、固定与自适应模式、
订单丢失、缓存故障、重置、主动结束和超时回收。

安全验证应确认跨会话操作、任意Docker参数、CSRF失败、直接访问内部服务
和删除最后实例均被拒绝。

## 14. 假设与实施期校准项

* 目标服务器为可运行Docker和Docker Compose的Linux主机。
* 部署者具有安装镜像、配置端口和执行管理脚本的权限。
* 实验镜像在开放测试前完成预拉取。
* 资源默认值需在目标4核8G服务器上基准测试后确认，但不得扩大产品范围。
* 前端具体图标、颜色和动画设计已明确延期，不影响后端状态数据契约。
* 当前接受公网IP加HTTP的风险，HTTPS是后续优先改进项。

没有阻塞SRS基线的产品级开放问题。
