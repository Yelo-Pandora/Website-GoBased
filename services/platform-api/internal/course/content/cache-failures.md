# 缓存故障

缓存跑得快，很容易让人忘记它也会失效、过期和停机。
平时藏在低延迟后面的数据库压力，可能在一个很短的时间段里全部回来。

平台把常见问题拆成四个可观察场景。
实验使用少量真实请求，再用教学倍率表现更大的业务规模。

## 缓存穿透

缓存穿透来自反复查询根本不存在的数据。
缓存里没有，数据库里也没有，每次请求都会一路查到底。

参数校验可以挡住明显不合法的编号。
空值缓存会暂时记住不存在的结果，布隆过滤器则先判断一个编号有没有可能存在。
这些办法都要设置边界，空值放得太久会影响后来新建的真实商品。

## 缓存击穿

一个热门商品刚好过期时，大量请求可能一起发现缓存为空。
如果每个请求都去数据库重建同一份数据，数据库会在那一刻承受重复工作。

单个应用可以合并同一时间的重复查询。
多个实例之间可以用带超时的互斥标记，只让一个实例负责重建。
提前续期也是一种选择，它用后台刷新换取更平稳的读取。

## 缓存雪崩

很多键在相近时间失效，回源请求会形成一波尖峰。
相同过期时间和 Redis 整体不可用都可能造成这种现象。

随机过期时间可以把失效时刻打散。
系统也可以预热常用数据、限制数据库回源速度，并在压力过高时返回有明确标记的降级内容。
降级保护了系统，用户看到的数据可能暂时不够新。

## Redis 重启

当前实验的 Redis 重启后，L2 内容会消失，因为实验明确关闭了持久化。
已有 L1 的实例还能返回部分热门数据，L1 未命中的请求会按当前策略访问数据库或得到降级结果。

Redis 恢复可用后，应用会随着读取逐步回填，也可以执行受控预热。
故障只应影响所属实验，其他用户的缓存和数据不能被碰到。

## 观察结果时看什么

实验会展示 L1 命中、Redis 命中、数据库回源、重建、限流和降级计数。
单看响应是否成功会漏掉压力转移过程。

保护策略也有成本。
互斥会增加等待，空值会占内存，布隆过滤器可能误判，降级会牺牲新鲜度。
选择策略时要看业务能接受哪一种代价。
