# 缓存故障

缓存运行正常时，商品查询很快，数据库只处理少量回源请求。
一批缓存失效后，原先被挡在前面的压力会重新落到数据库。
页面仍能返回结果，数据库连接和查询队列却可能已经接近上限。

课程把常见问题拆成四类理论场景。
当前平台不提供独立缓存故障实验，也不提供保护策略切换；这些内容用于解释真实系统中的风险与取舍。

## 缓存穿透

某个客户端不断查询商品 999999，而数据库里根本没有这个编号。
L1 找不到，Redis 也找不到，请求每次都会继续访问 MySQL。
数据库查完后只能返回不存在，下一次相同请求仍会重复整条路径。

参数校验可以挡住负数、超长编号等明显错误。
格式合法但不存在的编号，需要其他办法减少回源。
空值缓存会短暂记住不存在的结果，再次查询便能在缓存层结束。
这个空值不能保存太久，否则运营人员后来创建了该商品，用户仍可能看到不存在。

布隆过滤器可以提前判断一个编号是否可能存在。
判断为一定不存在时，请求不再访问数据库。
判断为可能存在时仍要继续查询，因为布隆过滤器会出现误判。
商品新增和删除后，过滤器内容也要跟着维护。

保护不能只看单个商品。
攻击者不断更换合法编号时，空值缓存会生成许多条目，内存同样会受到压力。
系统还需要限制请求速率和空值数量。

## 缓存击穿

商品 1001 正在促销，大量用户反复打开详情页。
它的缓存刚好过期，几十个请求几乎一起发现 L1 和 Redis 都没有数据。
这些请求若全部访问数据库，就会重复查询同一行，并争着把相同结果写回缓存。

单个应用实例可以合并同一时间的重复查询。
第一个请求负责读取数据库，后面的请求等待同一份结果，不再各自回源。
多实例场景还需要跨实例协调，可以使用带超时的互斥标记，让一台实例完成重建。

等待必须有上限。
负责重建的实例崩溃后，其他请求不能一直卡住。
互斥标记到期后，另一台实例应能接手，系统也要防止多个接手者再次形成并发回源。

热门数据还可以提前刷新。
缓存接近过期时，由后台任务重建内容，普通请求继续读取旧值。
这种办法让读取平稳一些，却增加了后台任务和短暂旧值管理。

## 缓存雪崩

一批商品在发布时使用了相同过期时间，半小时后几百个键在相近时刻失效。
每个商品只有少量请求，汇总后仍会形成明显的数据库尖峰。
Redis 整体不可用也会产生类似结果，原本分散在缓存层的读取一起回到数据库。

随机过期偏移可以把失效时间打散。
常用商品可以分批预热，数据库回源也要限制并发和速率。
压力超过保护线后，系统可以返回带有状态说明的降级内容，或者暂时拒绝部分低优先级请求。

降级保护了数据库，用户看到的数据可能较旧，某些功能也会暂时不可用。
团队要提前确定哪些商品信息允许使用旧值，哪些库存和订单操作必须等待真实数据。
把所有请求都放行，往往会让一次缓存故障继续拖垮数据库。

恢复过程也需要控制。
Redis 刚恢复时一次性回填全部热门商品，会再次产生尖峰。
分批预热和按实际读取逐步重建更慢，却更容易守住数据库容量。

## Redis 重启

多级缓存实验使用关闭持久化的临时 Redis，删除并重新创建后 L2 内容会消失。
实例 A 的 L1 仍保存部分热门商品，它可以继续返回这些内容。
实例 B 刚启动或没有对应条目，请求会按当前保护策略访问数据库，也可能得到降级结果。

这段时间里，不同实例的命中情况会明显不同。
页面将分别显示 L1 命中、Redis 未命中和数据库回源，读者可以看到压力从哪一层移到了哪一层。

Redis 恢复连接后，应用会逐步写回 L2。
连接恢复不等于缓存内容已经恢复，命中率需要一段时间才会上升。
Redis 只属于启动它的实验，重启和清理不能触碰其他用户的缓存键或实验数据。

## 观察结果时看什么

单看请求成功率会漏掉很多过程。
缓存故障早期，用户可能仍然拿到结果，数据库回源和连接等待却已经快速增加。
工程监控通常需要同时展示 L1 命中、Redis 命中、数据库回源、重建、限流、等待和降级计数。

这些指标要放在同一条时间线上看。
某个热门键失效后，Redis 命中下降，回源和互斥等待上升，重建完成后几项数据才会逐步恢复。
雪崩场景则会看到许多键共同失效，数据库压力持续时间也更长。

每种保护都有成本。
互斥增加等待，空值占用内存，布隆过滤器可能误判，限流会拒绝请求，降级会牺牲数据新鲜度。
业务能够接受哪种结果，决定了保护策略怎样组合。
