# 单机架构

你刚把一个商品网站做出来，每天只有几十个人访问。
手边只有一台服务器，把网页入口、Go 应用和 MySQL 都放进去，是很自然的选择。
用户打开商品页时，请求不用跨过很多机器，很快就能走完整条链路。

单机并不等于落后。
业务还小的时候，先把系统跑通，通常比一开始就拆成许多服务更重要。

## 一次商品查询怎样完成

用户输入商品编号后，请求先到 Nginx 或 Web 入口。
入口把请求交给 Go 应用，应用检查参数，再去 MySQL 查询商品名称、价格和库存。
数据库返回记录，应用整理响应，入口把结果送回浏览器。

这些组件分工不同，却使用同一台机器的 CPU、内存、磁盘和网络。
链路很短，排查也直观。
你可以沿着入口、应用、数据库的顺序检查，很少需要猜请求跑到了哪里。

## 为什么很多项目从单机开始

单机需要维护的东西少。
开发者准备好一台机器，就能部署完整业务，日志和监控也集中在一个地方。
代码更新失败时，回退这一处环境即可。

小团队尤其适合从这里起步。
大家可以把时间花在商品、订单和数据正确性上，不必马上维护服务发现、内部网络和多套发布流程。

学习架构时，单机也是一个清楚的起点。
你先看懂完整请求，再去学习应用拆分和集群，就容易发现每次改造究竟解决了什么。

## 共享资源会怎样互相影响

平时请求不多，共享资源很难让人察觉。
流量一上来，问题就会连在一起。

一条慢查询长时间占用磁盘，后面的商品请求会排队。
应用生成大报表时吃掉大量内存，MySQL 能用于缓存数据的空间也会减少。
访问日志不断增长，还可能把数据库和备份需要的磁盘空间挤满。

页面此时也许还能打开，但机器已经没有多少余量。
下一次发布、备份或流量上涨，都可能让响应明显变慢。

## 换一台更大的机器能解决多少问题

给服务器增加 CPU、内存和更快的磁盘，叫作纵向扩容。
它改动小，见效也快，常常能给业务争取一段时间。

纵向扩容有上限。
更大的机器更贵，升级时可能需要停机，硬件也不可能一直往上加。
应用和数据库仍在争用同一套资源，只是可用空间暂时变大了。

如果团队没有找到真正的瓶颈，业务继续增长后，系统往往还会在相同位置卡住。

## 单机故障为什么影响很大

单机里的入口、应用和数据库处在同一个故障范围。
机器断电、磁盘损坏或系统无法启动时，用户看不到商品，应用也无法继续处理订单。

备份只能保存数据，不能自动恢复整套服务。
团队还要准备新机器、安装环境、恢复数据，再确认业务能否正常运行。
最近一次备份之后写入的订单能不能找回，也需要提前说明。

把备份放在原机器的另一个目录里帮助不大。
机器整体损坏时，这些文件仍然拿不到。
备份放到独立位置，并实际做过恢复演练，才知道停机大概要持续多久。

## 什么情况下单机已经够用

原型、内部工具、小流量网站和学习环境，都可以长期使用单机。
只要流量平稳，业务能接受短暂停机，简单方案就更容易维护。

是否拆分，要看具体问题。
应用发布经常拖慢数据库、备份持续影响页面、资源需求差异越来越大，都是值得拆分的信号。
只因为访问量增加一点就急着拆，反而会多出网络、权限和运维问题。
