# 单机架构

一家小店刚上线时，每天只有几十个人浏览商品，偶尔有人提交订单。
团队手里只有一台机器，于是把网页入口、业务处理和数据存储都放了进去。
用户打开商品页，几步处理在同一台机器里接连完成，部署和排查问题都很直接。

这样的起点很常见，也很实用。
流量不大时，团队更需要尽快把完整业务跑通，复杂的拆分只会增加维护工作。

## 一台机器承担了什么

用户查询一件商品时，请求先到页面入口。
入口把请求交给应用，应用检查商品编号和访问条件，再去数据库读取名称、价格和库存。
数据库返回结果后，应用整理响应，入口再把页面内容送回用户。

这些职责在逻辑上分得开，运行时却共享同一套处理器、内存、磁盘和网络。
平常看不出问题，繁忙时影响会连在一起。
一条缺少合适索引的查询占住磁盘，后面的商品请求便开始排队。
应用为了生成一份大报表吃掉很多内存，数据库可用的缓存空间也会跟着减少。

磁盘尤其容易被忽略。
业务数据、访问日志、临时文件和备份文件都写在同一处，任何一项增长过快都可能挤压其他部分。
页面还能打开，并不代表机器还有足够余量承受下一次发布或备份。

## 它为什么常被用作起点

单机架构需要管理的东西少。
开发者准备一台机器就能跑通完整请求链，发布时只需确认这一处环境，日志和监控也集中在一起。
出了问题，团队可以沿着入口、应用、数据库的顺序检查，不必先确认请求究竟去了哪台机器。

要维护的东西少，成本也会下降。
小团队不用维护额外网络、服务发现和多套发布流程，也不用过早处理分布式状态。
需求还在频繁变化时，少一些运行边界，通常能让修改更快落地。

单机也方便学习。
一次请求从进入系统到读取数据的过程都看得见，后续再拆分应用和数据库时，读者能清楚比较请求路径发生了什么变化。

## 容量会在哪里碰到上限

流量增加后，团队应先看机器到底忙在哪里。
处理器长时间接近上限，可能是应用计算太多。
磁盘等待升高，可能是数据库查询或日志写入过重。
内存不足则会让应用和数据库频繁回收缓存，请求延迟也会跟着抖动。

直接换更大的机器叫纵向扩容。
增加处理器、内存和更快的磁盘，确实能给业务争取时间，而且改动比拆分系统小。
它也受机器规格、采购成本和升级窗口限制。
某些升级需要停机，旧机器空出来后未必能立刻派上用场。

更大的机器也没有消除共享资源问题。
应用、数据库和日志仍在争用同一套硬件，只是可用空间暂时多了一些。
团队若没有找出真正的瓶颈，下一次增长仍可能在相同位置卡住。

## 故障和恢复要单独考虑

单机最难回避的是故障范围。
机器断电、磁盘损坏或系统无法启动时，入口、应用和数据会一起中断。
此时用户看不到商品，团队也无法在原机器上继续处理订单。

备份只能保存某个时间点的数据。
真正恢复服务还要准备新机器、安装运行环境、恢复数据并验证业务是否正常。
最近一次备份之后写入的内容能否找回，也要提前说清楚。

团队可以接受多长时间的停机，决定了恢复准备要做到什么程度。
只把备份文件放在原机器的另一块目录里，机器整体损坏时帮助不大。
定期把备份放到独立位置，并实际做一次恢复演练，才能知道这条退路要花多久。

## 什么时候够用

原型、内部工具、小流量网站和学习环境通常可以从单机开始。
业务能够接受短暂停机，流量变化也较平稳时，简单方案更容易维护。
团队人数很少的情况下，把精力放在业务和数据正确性上，往往比维护多套基础设施更划算。

拆分应由具体问题推动。
应用发布频繁影响数据库，备份持续拖慢页面，资源增长方向明显不同，或者单机恢复时间已经超出业务承受范围，这些都是可以讨论的信号。
只因为访问量有所增加就立即拆分，可能会把一个清楚的问题变成几组新的网络和运维问题。

## 在本平台里怎么学

这门课程只提供理论内容，不创建一台塞入所有组件的实验容器。
后面的应用与数据分离实验会把请求处理和数据存储放到不同运行单元。
回头对照这里的请求路径、共享资源和故障范围，就能看出那次拆分解决了哪些牵连，也能看见它新增的网络成本。
