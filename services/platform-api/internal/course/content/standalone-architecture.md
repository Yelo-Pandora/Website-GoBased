# 单机架构

一家小店刚上线时，每天只有几十个人浏览商品。
页面入口、订单处理和数据存储全放在一台机器上，已经够用。
请求进来后不用跨机器传递，部署和排查问题也很直接。

## 一台机器承担了什么

用户发起商品查询，入口接住请求，应用处理业务，数据库取出商品。
这些工作都在同一台机器里完成。
它们仍是不同职责，只是暂时共享处理器、内存、磁盘和网络。

共享资源让系统容易起步，也会让各部分互相影响。
一次耗时较长的查询可能占住数据库和磁盘，应用随后的请求只好一起等。
日志突然写得很多，也可能挤掉业务需要的磁盘空间。

## 它为什么常被用作起点

单机架构需要管理的东西少。
开发者只要准备一台机器，就能把完整请求链跑起来。
小流量阶段很少需要复杂的故障协调，备份、监控和发布也容易理解。

学习系统架构时，从这里出发很合适。
你能先看清一次请求经过哪些环节，再研究为什么要把这些环节拆开。

## 容量会在哪里碰到上限

机器可以增加处理器、内存和更快的磁盘，这种做法叫纵向扩容。
它能争取时间，却受机器规格和成本限制。
升级时通常还要停机，旧机器闲下来后也未必容易利用。

更棘手的是单点故障。
机器断电、磁盘损坏或系统无法启动时，入口、应用和数据会一起不可用。
只有备份还不够，恢复数据和重新提供服务都需要时间。

## 什么时候够用

原型、内部工具、小流量网站和学习环境通常可以从单机开始。
如果业务能接受短暂停机，团队也没有持续扩容的压力，简单方案更省心。

访问量增长后，先观察真正吃紧的资源。
应用计算繁忙和数据库查询繁忙需要不同的处理办法，盲目换一台更大的机器很容易把问题往后拖。

## 在本平台里怎么学

这门课程只提供理论内容，不创建一台塞入所有组件的实验容器。
后面的实验会从应用与数据分离开始。
回头对照单机架构，你会更容易看出每次拆分解决了什么，又增加了哪些麻烦。
