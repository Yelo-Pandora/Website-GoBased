# 多级缓存

商品详情被反复查询时，每次都访问数据库很浪费。
缓存保存一份近期结果，让多数读取走更短的路，数据库可以把资源留给真正需要查询和更新的请求。

缓存更适合读得多、改得少的数据。
价格和商品说明频繁变化时，团队还要把更新后的正确性放在速度前面。

## 三层读取路径

本平台先查应用实例自己的进程内缓存，也就是 L1。
它离请求处理最近，没有额外网络往返，但每个实例各自保存一份。

L1 没有命中时，应用再查当前实验共享的 Redis，也就是 L2。
多个实例可以看到同一份 Redis 数据，代价是多一次网络访问。

Redis 也没有数据时，应用才访问 MySQL。
查到结果后先回填 Redis，再放入当前实例的 L1，后续请求便能更快返回。

## 缓存键要让人看得懂

一个键要能区分实验、数据类型和商品编号。
命名空间可以防止不同实验碰到同名数据，稳定编号能保证相同查询落到同一个键。
键也不能无限变长，否则内存和传输成本会跟着增长。

缓存内容需要过期时间。
过期太短会频繁回源，过期太长又会让旧数据停留更久。
给相近数据加入少量随机过期偏移，可以减少它们在同一秒集中失效。

## 商品更新后怎么处理

数据库仍是商品数据的事实来源。
更新商品时，系统先写数据库，再删除 Redis 中的旧值。
Redis 会发布失效通知，各应用实例收到后清掉自己的 L1。

通知传播需要一点时间，短暂的旧值窗口无法完全消除。
页面会展示各实例看到的版本，方便观察一致性怎样恢复。

## 多一层也多一份责任

L1 减少了 Redis 访问，却带来多实例缓存失效问题。
Redis 分担数据库压力，也增加了网络依赖和新的故障点。
每一层都要限制条目数量、有效时间和重建速度。

缓存命中率高并不等于系统一定健康。
还要观察回源次数、重建次数、旧值窗口和故障时的降级结果。
