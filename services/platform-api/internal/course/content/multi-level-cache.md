# 多级缓存

商品促销页会反复展示同一批热门商品。
如果每次刷新都查询 MySQL，数据库会把大量时间花在重复读取上。

缓存会保存近期查询结果，让后来的请求少走几步。
本平台使用两层缓存，应用进程里的 L1 离代码最近，Redis 是多台应用可以共用的 L2。
两层都找不到数据时，请求才会到 MySQL。

## 一次查询怎样经过三层

用户第一次查询商品 1001，应用先检查当前实例的 L1。
实例刚启动，L1 里还没有这件商品，于是继续查询 Redis。
Redis 也没有，应用只能访问 MySQL。

MySQL 返回商品后，应用先把结果写入 Redis，再放进本实例的 L1，最后返回给用户。
第二次请求若仍落到这个实例，可以直接从 L1 返回。

另一台实例的 L1 是独立的。
它第一次查询商品 1001 时会访问 Redis，再把结果复制到自己的 L1。
多台实例共享 Redis，却各自保存 L1，这也是后面一致性问题的来源。

> 在实验中，点击 `发送一批`，先看第一次请求落到 MySQL，再看后续请求停在 Redis 或 L1。
> 动画、分层计数和条目清单会一起更新。

## L1 和 Redis 各自省掉了什么

L1 位于应用进程内部，不需要网络访问，读取很快。
它的容量有限，实例重启后内容也会消失，每台实例还要维护自己的副本。

Redis 多了一次网络往返，却能让多台应用共用缓存内容。
实例扩容后，新实例可以从 Redis 读取热门商品，不必把所有数据重新查一遍 MySQL。

多一层缓存，也会多一份配置和故障处理。
条目数量、过期时间、内存占用和重建速度都要有人管理。

> 对同一商品连续点击 `发送一批`，可以比较 L1、Redis 和 MySQL 的命中计数。
> 再增加一台实例，新实例会先经过 Redis，随后才建立自己的 L1。

## 缓存键为什么要有清楚边界

缓存键需要区分实验、数据类型和商品编号。
实验标识防止不同用户使用同名数据，商品编号让相同查询落到同一个键。
数据结构改变时，还可以加入版本，避免新旧格式混在一起。

键太长会多占内存和传输空间。
把时间戳等不断变化的字段塞进键里，还会生成许多只访问一次的条目，缓存很快就被填满。

缓存内容还要设置过期时间，也就是 TTL。
TTL 太短，数据刚写进去就失效，MySQL 仍要处理许多重复查询。
TTL 太长，商品已经更新，旧值可能继续留在缓存里。

相近商品可以加入少量随机过期偏移。
这样它们不会在同一秒一起失效，数据库收到的回源压力会更平缓。

> 连续发送不同商品批次时，条目清单会显示缓存键、数据版本和剩余 TTL。
> 这些值来自 Lab App 和 Redis 当前保存的内容。

## 商品更新后为什么不能只改数据库

MySQL 仍是商品数据的来源。
运营人员修改价格后，系统通常先确认数据库写入成功，再删除 Redis 中的旧值。
Redis 可以发布失效通知，让各应用实例清理自己的 L1。

通知传播需要时间。
实例 A 已经删除旧值，实例 B 可能晚一点收到通知，短时间内仍会返回旧价格。

删除缓存和下一次回填之间也会发生竞争。
一个慢查询先读到旧数据，商品随后完成更新，慢查询却在更新后把旧结果写回缓存。
数据版本、更新顺序和 TTL 都可以帮助系统识别这种旧值。

商品说明允许短暂旧值时，可以使用较长 TTL 来减少回源。
库存和订单状态更敏感，通常需要更严格的版本检查或直接读取权威数据。

> 当前实验不模拟商品写入和失效通知。
> 你可以使用 `去除 L1` 或 `去除 Redis` 改变读取路径，观察旧缓存层不在时，请求怎样向下回源并重新建立条目。

## 去掉一层缓存后会发生什么

去掉某台实例的 L1 后，这台实例的请求会先访问 Redis。
Redis 命中时，MySQL 压力不会明显增加，但每次读取都会多一次网络往返。

去掉 Redis 后，已有 L1 的实例还能返回部分热门商品。
L1 未命中的请求会直接访问 MySQL，数据库回源数会增加。

如果 L1 和 Redis 都不可用，每次商品查询都要访问 MySQL。
页面仍可能返回结果，响应时间和数据库压力却会明显上升。

> 使用 `去除 L1`、`添加 L1`、`去除 Redis` 和 `添加 Redis`，可以组合不同缓存层。
> 对同一批商品发送请求时，命中分布会随着层级配置改变。

## 缓存穿透怎样发生

某个客户端不断查询商品 999999，而 MySQL 里没有这个编号。
L1 找不到，Redis 也找不到，请求每次都会继续访问 MySQL。
数据库只能返回不存在，下一次相同请求又会重复整条路径。

参数校验可以挡住负数和超长编号等明显错误。
格式正确但不存在的商品，可以短暂缓存为空值，让后续请求在缓存层结束。
空值不能保存太久，否则商品后来创建成功，用户仍会看到不存在。

布隆过滤器也能提前判断编号是否可能存在。
它判断一定不存在时，请求不再访问 MySQL。
它判断可能存在时仍要继续查询，因为这种结构会有误判。

攻击者还可能不断更换合法编号。
系统需要限制请求速率和空值数量，避免保护措施自己占满内存。

## 缓存击穿怎样发生

商品 1001 正在促销，许多用户反复打开详情页。
它的缓存刚好过期，几十个请求几乎一起发现 L1 和 Redis 都没有数据。
这些请求若全部访问 MySQL，就会重复查询同一行。

单个实例可以合并同一时刻的重复查询。
第一个请求负责读取数据库，后面的请求等待同一份结果。

多实例场景还需要跨实例协调。
一台实例取得带超时的互斥标记后负责重建，其他实例等待结果。
负责重建的实例若崩溃，标记到期后必须允许别的实例接手。

热门商品也可以在快过期时由后台任务提前刷新。
普通请求继续读旧值，后台慢慢准备新内容，但团队要能接受这段短暂旧值时间。

## 缓存雪崩怎样发生

一批商品在发布时使用了相同 TTL。
半小时后，几百个键在相近时刻失效，每个商品只有少量请求，合起来仍会形成数据库尖峰。

Redis 整体不可用时也有类似结果。
原本停在缓存层的读取，一起回到 MySQL。

随机 TTL、分批预热和限制回源并发，可以把压力摊开。
压力超过保护线后，系统还可以暂时拒绝低优先级请求，或返回允许使用的旧数据。

库存和订单不能随便使用旧值。
团队要提前分清哪些字段可以降级，哪些操作必须等待权威数据。

Redis 恢复后也不能一次回填所有热门商品。
分批预热或跟随实际请求逐步重建会慢一些，却更容易守住 MySQL 容量。

> 当前实验没有穿透、击穿和雪崩的保护策略开关。
> 你可以去掉 Redis 或 L1，再观察请求向 MySQL 集中的过程，理解缓存失效为什么会放大数据库压力。

## Redis 重启后为什么不会马上恢复命中率

本平台的实验 Redis 不保存持久化数据。
执行 `去除 Redis` 再执行 `添加 Redis` 后，新的 Redis 是空的。

已有 L1 的实例仍可能返回部分热门商品。
新实例或 L1 未命中的请求会访问 MySQL，再把结果写回 Redis。
不同实例在这段时间里的命中情况可能差很多。

Redis 能重新连接，只说明通道恢复了。
缓存内容还要随着读取逐步建立，命中率需要一段时间才会上升。

> 先发送几批商品建立缓存，再执行 `去除 Redis` 和 `添加 Redis`。
> 页面会显示 Redis 不可用、MySQL 回源以及恢复后逐步回填的过程。

## 观察缓存实验时看哪些数字

请求成功并不代表缓存一切正常。
Redis 刚出问题时，用户可能仍能拿到商品，MySQL 回源和连接等待却已经增加。

先看 L1 命中、Redis 命中和 MySQL 回源。
再看 Redis 不可用、L1 已关闭和实际查询次数，这些数字能解释请求为什么走到更深的一层。

指标要放在同一段时间里看。
某个缓存层被移除后，上层命中下降，下层回源上升，重新添加后，条目和命中率才会慢慢恢复。

每种保护都有成本。
互斥会增加等待，空值占用内存，布隆过滤器可能误判，限流会拒绝部分请求。
选择哪种组合，要看业务能够接受什么结果。

> 组合使用缓存层操作和 `发送一批`，再对照分层计数、条目清单和请求动画。
> 不要只盯着命中率，MySQL 回源和恢复速度同样重要。
