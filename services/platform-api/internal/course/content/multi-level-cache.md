# 多级缓存

促销页面反复展示同一批热门商品，几秒内会收到许多内容相同的查询。
每个请求都访问数据库，会把磁盘和连接资源花在重复工作上。
缓存保存近期结果，让常见读取走更短的路径，数据库可以处理真正需要查询和更新的数据。

缓存适合读得多、改得少的内容。
价格、库存和商品说明变化频繁时，读取速度要和数据新鲜度一起考虑。

## 一次查询经过三层

用户第一次查询商品 1001，应用先检查当前实例的进程内缓存，也就是 L1。
刚启动的实例还没有这件商品，L1 返回未命中。
应用接着查询实验共享的 Redis，也就是 L2，Redis 此时也没有数据。

请求继续到 MySQL。
数据库读出商品名称、价格和数据版本，应用把结果写入 Redis，再放进本实例的 L1，然后返回给用户。
第二次相同查询落到这个实例时，可以直接从 L1 返回，不需要网络访问。

另一台应用实例收到相同请求时，它自己的 L1 可能为空。
这次查询会访问 Redis，并把 Redis 里的结果复制到本地 L1。
多台实例共享 L2，却各自保存 L1，读取速度提高了，一致性处理也变得更复杂。

L1 距离请求处理最近，访问开销很小。
它的容量有限，实例重启后内容也会消失。
Redis 多了一次网络往返，但不同实例可以读取同一份缓存，数据库回源次数会明显减少。

## 缓存键需要稳定边界

一个键要能区分实验、数据类型和商品编号。
实验标识避免不同用户碰到同名数据，商品编号保证相同查询落到同一个键。
数据结构发生变化时，还可以在命名中加入版本，防止新旧格式混在一起。

键名要清楚，也要控制长度。
过长的键会占用更多内存和传输空间，频繁拼接变化字段还可能制造大量只访问一次的缓存条目。
查询条件很多时，团队应明确哪些条件会真正改变结果。

缓存内容需要过期时间。
时间太短，数据刚写进去就失效，数据库仍会收到大量重复查询。
时间太长，商品已经更新，旧值却可能继续留在缓存里。
给相近商品加入少量随机过期偏移，可以减少一批键在同一秒失效。

## 商品更新后会发生什么

数据库仍是商品数据的事实来源。
运营人员修改商品价格时，系统先确认数据库写入成功，再删除 Redis 中的旧值。
Redis 发布失效通知，各应用实例收到后清理自己的 L1。

通知传播需要时间。
实例 A 已经删除旧值，实例 B 可能晚一点收到通知，短时间内仍返回旧价格。
设计中的页面将展示各实例看到的数据版本，读者可以观察旧值窗口怎样出现，又怎样在通知和重新读取后消失。

删除缓存和下一次回填之间也可能发生竞争。
一个慢查询先读到旧数据，商品随后完成更新，慢查询却在更新后把旧结果写回缓存。
系统需要结合数据版本、更新顺序和过期时间控制这种情况，不能只把删除缓存当成完整答案。

对新鲜度要求很高的数据，缓存时间应更短，读取时也可能需要额外版本校验。
允许短暂旧值的商品说明，可以使用更长时间来换取较少回源。
选择应来自业务能接受的结果，而非单纯追求高命中率。

## 每多一层都要付出管理成本

L1 减少了 Redis 访问，却让每个实例保存自己的副本。
Redis 分担数据库压力，也增加了网络依赖和新的故障点。
每层都要限制条目数量、有效时间和重建速度，避免缓存自己吃掉过多内存。

缓存满了以后要淘汰旧条目。
热门商品通常会再次被读入，冷门商品则可能只访问一次便离开缓存。
条目上限过小会频繁淘汰，过大又会挤压应用处理请求所需的内存。

命中率高只能说明多数请求找到了缓存。
团队还要观察数据库回源、缓存重建、旧值持续时间和通知失败后的恢复过程。
某个错误值被大量命中时，漂亮的命中率反而会把问题藏得更深。

## 故障时读取路径会改变

Redis 暂时不可用时，已有 L1 的实例还能返回部分热门商品。
L1 未命中的请求需要受控回源，不能让所有流量立刻压到数据库。
系统可以限制并发回源，并在数据库压力过高时返回带有明确状态的降级结果。

Redis 恢复后，应用会随着读取逐步回填缓存。
一次性预热太多商品也会制造新的数据库尖峰，所以恢复速度同样需要限制。
缓存层恢复可用，只代表通道回来了，内容仍要慢慢重建。
