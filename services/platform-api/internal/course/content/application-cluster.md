# 应用集群与负载均衡

促销开始后，商品详情请求从每秒几次增加到几十次。
一台应用的请求队列越来越长，团队加了第二台应用，却发现用户仍然只会访问原来的入口。
多出一台机器还不够，系统需要一个统一地址，把到来的请求分给当前可以工作的实例。

这个统一入口承担负载均衡。
用户不需要记住实例地址，应用扩容和替换也可以在入口后完成。

## 请求怎样进入集群

用户发送商品查询时，请求先到内部负载均衡入口。
入口查看可用实例和当前分配规则，选出一台应用，再把请求转发过去。
应用读取共享数据库并返回商品，响应沿原路回到用户。

连续八个请求到来时，入口可能把其中四个交给实例 A，另外四个交给实例 B。
实例 B 暂时退出后，入口要停止向它发送新请求。
等健康检查确认它恢复，入口才能把它重新放回可用列表。

负载均衡器处理的是请求去向。
应用实例仍要共享正确的数据来源，登录状态和用户操作也不能只存在某一台实例里，否则下一次请求换到另一台机器时就会丢失上下文。

## 常见的分配办法

轮询按顺序选择实例。
A 接一个，B 接一个，然后再回到 A。
几台机器性能接近、请求耗时也相近时，这种办法简单而且容易核对。
实例 B 因磁盘等待变慢后，轮询仍会把相同比例的请求交给它，B 的队列可能越积越长。

加权轮询给实例设定不同份额。
A 的处理能力约为 B 的两倍时，可以让 A 接到更多请求。
权重表达的是团队希望怎样分配，机器的真实容量发生变化后，旧权重不会自己变得合理。

IP 哈希根据用户来源选择实例，同一来源通常会落到同一台机器。
它能保持一定的访问黏性，但公司网络或移动运营商可能让许多用户共用一个出口地址。
这些请求被集中到同一实例时，分配结果会偏斜。

最少连接倾向于选择当前连接较少的实例。
请求处理时间差异很大时，它比固定轮询更能避开正在处理长任务的机器。
入口需要持续维护连接状态，连接少也未必等于处理器和数据库访问都很空闲。

响应时间策略会参考近期请求速度。
某台实例连续变慢后，入口可以减少给它的请求。
短暂抖动很常见，系统若追着每次变化调整，流量会在实例之间来回摆动。
平滑窗口和冷却时间可以让调整慢一点。

## 健康和容量要分开看

健康检查回答实例还能不能接收请求。
一个实例能够返回健康响应，只能说明进程仍在工作。
它可能正在处理大量慢查询，商品请求已经排队，剩余容量很少。

平台设计中会另外计算教学等效容量和相对负载。
实验将只发送较低速率的真实请求，再用教学倍率表示更大的业务压力，避免为了演示过载而把宿主机处理器跑满。
页面将分开显示真实请求速率、等效负载和实例容量。

当等效负载超过实例的有效容量，实验将记录模拟订单丢失或延迟增加。
这些结果用于解释分配策略，不代表平台真的制造了同等规模的外部流量。

## 固定权重会暴露什么

固定模式保留用户设定的权重。
A 和 B 原本各接一半请求，B 的有效容量下降后，入口仍按原比例转发。
B 的队列开始增长，A 还有余量，页面将显示流量分配和处理能力不匹配。

这种模式适合学习权重的含义。
权重不是实例性能的实时测量值，也不能保证每个短时间窗口都严格符合比例。
请求数量少、请求耗时不同或实例刚刚恢复时，实际结果都会有偏差。

## 自适应权重怎样收敛

自适应模式会读取实例的有效容量和稳定负载，计算新的目标比例。
控制器要等容量变化持续一段时间，才减少发往慢实例的请求。
两次调整之间还会保留冷却时间，让上一轮配置有机会产生可观察结果。

当 B 恢复容量时，权重也不会立刻跳回原值。
逐步恢复可以避免刚启动的实例马上接到大量请求，也能减少配置频繁改动。
负载均衡配置应用失败时，系统应保留上一份可用配置，不能让一次调整切断整个实验入口。

权重调整无法创造容量。
总请求超过所有实例能够处理的数量时，改变比例只能移动压力。
团队仍要增加实例、恢复慢实例的性能，或者限制进入系统的流量。
