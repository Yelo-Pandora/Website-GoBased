# 应用集群与负载均衡

一台应用忙不过来时，最直接的办法是再加几台。
用户却不该记住每台机器的地址，也不该靠运气挑一台。
集群前需要一个统一入口，把请求交给当前可用的应用实例。

这个入口承担负载均衡。
它帮助系统利用多台机器的处理能力，也能在某台机器故障时绕开它。

## 常见的分配办法

轮询会按顺序把请求交给不同实例。
几台机器性能接近、请求耗时也相近时，它简单而且容易预测。
某台机器变慢后，轮询仍会继续分配请求，压力可能越积越多。

加权轮询给每台机器一个比例。
性能好的机器多接一些请求，性能较弱的机器少接一些。
权重反映的是分配意图，机器的真实容量变了，权重也要有人更新。

IP 哈希会根据用户地址选择实例，同一来源通常会落到同一台机器。
它能维持一定的访问黏性，但大流量来源可能把单台机器压得很重。
许多用户共用出口地址时，分配也容易偏斜。

最少连接会优先选择当前连接较少的实例。
长时间保持连接的业务更适合这种办法。
入口需要持续掌握连接数，繁忙时会增加监测和判断成本。

最短响应时间依赖近期观测结果，把请求倾向于响应较快的实例。
短暂抖动可能让权重来回变化，所以实际系统通常会使用平滑窗口和冷却时间。

## 健康和容量要分开看

健康检查回答实例能不能接请求。
通过健康检查只说明服务还活着，不代表它还有足够容量。

平台会另外计算教学等效容量和相对负载。
实例负载超过有效容量后，实验会显示订单丢失，但不会真的把宿主机处理器跑满。
页面也会把真实请求速率和教学倍率分开显示。

## 固定权重和自适应权重

固定模式保留当前权重。
当一个实例的性能下降时，请求比例不跟着变化，你能直接看到分配失衡和过载。

自适应模式会参考有效容量和稳定负载，逐步调整目标比例。
控制器不会追着每次波动改配置，它要等变化持续一段时间，并在两次调整之间留出冷却时间。

无论怎样调整权重，集群总容量都有上限。
总请求超过所有实例能够处理的数量时，挪动比例只能改变压力落在哪里。
这时需要扩容、恢复实例性能或降低流量。
