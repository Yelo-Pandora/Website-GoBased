# 应用与数据分离

商品越积越多以后，应用发布和数据备份开始互相打扰。
团队想更新页面和业务规则，却不愿每次都碰存放商品与订单的机器。
把应用和数据库放到不同运行单元，能先解开这层牵连。

## 请求多走了一段路

用户查询商品时，请求先到应用。
应用检查参数和业务规则，再通过内部网络向数据库取数据。
数据库返回结果，应用整理后交给用户。

这条路比单机多了一次网络往返。
网络会有延迟，也可能断开，所以应用要限制等待时间并管理好数据库连接。
连接开得太少，请求会排队；开得太多，数据库又会被连接本身拖累。

## 分开之后得到什么

应用和数据库可以按自己的节奏调整资源。
商品查询需要更多计算能力时，可以先扩应用。
数据量增长时，可以把精力放在数据库的内存、磁盘和索引上。

发布边界也清楚了。
替换应用不需要搬动数据，数据库备份也不必跟着页面发布一起进行。
权限可以收紧，应用只拿到业务所需的读写能力，数据库管理入口留在受信环境。

## 新问题不会自己消失

数据库现在成了所有数据请求都要经过的共享依赖。
应用运行正常时，数据库故障仍会让商品查询失败。
查询越来越多以后，数据库也可能成为新的容量瓶颈。

网络分开还带来了超时、重试和重复操作问题。
一次写入已经成功，但响应在路上丢了，应用可能误以为失败并再次提交。
后续课程会用幂等和状态记录处理这类情况。

## 在实验里观察什么

平台会创建一个应用实例和一套独立实验数据。
商品查询真实经过内部网络访问数据库。
你可以沿着请求路径查看应用身份、数据库连接和返回结果。

这个阶段仍只有一个应用实例。
它解决了职责和资源混在一起的问题，还没有解决应用单点故障与横向扩容。
下一步才会加入应用集群和负载均衡。
