# 应用与数据分离

周五晚上，网店要更新商品搜索规则，MySQL 同时在做备份。
应用发布和数据库备份都要用 CPU、内存和磁盘，放在同一台机器上时，很容易互相拖慢。

团队于是把 Go 应用和 MySQL 放到不同运行单元。
应用负责接收请求和处理业务，数据库负责保存商品与订单，两边通过内部网络通信。

## 请求为什么多走了一段路

用户查询商品时，请求先到 Go 应用。
应用检查商品编号和访问条件，再从连接池取出一条连接，把查询发给 MySQL。
数据库找到商品后返回记录，应用整理字段，再把结果交给用户。

单机里的一次本地调用，现在变成了网络请求。
网络可能变慢，也可能短暂断开。
应用本身还在运行，并不代表它此刻一定能联系到数据库。

等待时间需要有上限。
一个查询迟迟没有结果时，应用应当释放请求和连接，让后面的用户还有机会得到响应。

> 在实验中，点击 `创建实验` 后，页面会出现一个 Lab App 和共享 MySQL。
> 拓扑会把它们之间的网络边界画出来，你可以顺着箭头查看新的请求路径。

## 连接池为什么不能随便调大

每次查询都重新建立数据库连接会很慢，所以应用通常复用一组连接，这就是连接池。
连接太少时，请求会在应用里排队，MySQL 明明还有余量，却收不到更多查询。

连接太多也会出问题。
每个应用实例都占住一批连接，MySQL 要花内存维护它们，真正执行查询的资源反而变少。

以后增加应用实例时，不能只看实例数量。
实例数乘以每个实例的连接上限，才是数据库可能面对的连接总量。

> 当前实验使用固定连接配置，没有单独的连接池调节按钮。
> 你可以在拓扑中确认多个运行单元仍然共用同一个 MySQL，并理解扩容时为什么要计算连接总数。

## 发布和数据为什么更容易分开管理

应用与数据库分开后，两边可以按自己的节奏调整。
商品查询增加时，团队先处理应用容量。
商品数据变多时，MySQL 更需要内存、磁盘和合适的索引。

发布范围也缩小了。
替换应用时，商品和订单仍留在数据库里。
应用版本有问题，团队回退应用即可，通常不用搬动数据。

权限也更清楚。
应用账号只拿到业务需要的查询和写入权限，建库、改账号等管理操作留在受信环境。
MySQL 不必暴露到公网，只允许指定应用通过内部网络访问。

> 点击 `重置` 时，Orchestrator 会重新应用当前场景配置。
> 页面会显示 Lab App 和路由重新建立，而隔离的 MySQL 数据仍由数据库单独管理。

## 网络超时后能不能直接重试

商品查询失败后，再读一次通常不会修改数据，所以重试相对简单。
订单写入就不同了。

MySQL 可能已经保存订单，只是成功响应在返回途中丢失。
应用看到超时后直接再写一次，就可能生成两份订单。

常见做法是给一次操作分配唯一标识。
应用重试时，数据库先检查这个操作是否已经完成，再决定返回旧结果还是继续执行。
这个处理方式叫幂等。

超时也不能一味拉长。
过短会把正常的慢查询当成失败，过长会让连接一直被占用。
团队要根据平时的响应时间和失败后的处理方式来设置边界。

> 结束实验后再次点击 `新建实验`，Platform API 会为每次生命周期操作生成唯一标识。
> 操作记录会显示重复请求怎样复用已有结果，或等待前一次操作完成。

## 数据库为什么仍可能成为瓶颈

应用拆出去以后，MySQL 仍要处理所有商品和订单请求。
增加应用实例不会自动增加数据库容量。

查询缺少索引、连接过多或磁盘变慢时，前面的应用会一起排队。
只看应用 CPU 很容易误判。
还要结合连接等待、查询时间和磁盘状态，才能知道慢在哪里。

共享数据库仍然有价值。
数据规模可控时，一份明确的数据来源能减少复制和多库协调问题。
等 MySQL 长期成为瓶颈，再学习读写分离或分片会更容易理解。

> 刷新实验快照时，Platform API 会重新读取 Lab App、共享 MySQL 和 Nginx 网关状态。
> 你可以看到应用已经独立运行，但数据库仍是所有请求共用的依赖。

## 这一步解决了什么

应用与数据分离后，发布、资源和权限的边界清楚了。
应用单点故障仍然存在，因为当前场景只有一个 Lab App。

下一门课程会在请求入口后放入多台应用实例，再由 Nginx 分配流量。
新的问题也会跟着出现，包括实例健康、容量差异和流量分配。

> 使用 `创建实验`、`重置` 和 `结束`，可以观察应用资源与数据资源拥有不同生命周期。
> 拓扑、状态标签和操作记录会同步显示每一步发生了什么。
